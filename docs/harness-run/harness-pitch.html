A REFERENCE FOR AI-DRIVEN SECURITY HARNESSES

The pitch

Security teams don't have a bug-finding problem. They have a proof problem.

Scanners are cheap; certainty is expensive. Every tool hands you a longer list of maybe. A security harness is the machine that turns that firehose into a short list of proven, ranked, owned issues — and then keeps going, past find-and-fix, into detect-and-respond.

Why the old shape fails

A list of findings is not a decision.

A static scanner says "SQL injection at line 21." Is it reachable? Exploitable in your deployment? Already mitigated by the framework? The scanner can't say — so a human re-derives every finding by hand. That human is the bottleneck, and they burn out on false positives long before the real bug.

Meanwhile the tools stop at the finding. They don't prove it, don't rank it by real exploitability, don't propose the fix, and go completely silent the moment an attacker actually shows up in your logs.

The bottleneck was never finding bugs. It's trusting the answer.

The job that matters is the loop around the finding: model → discover → prove → triage → fix → hunt → respond. Automate that loop with verifiable output, and the human moves from grinding a queue to approving a short, trustworthy list.

The approach — one closed loop

The whole security lifecycle, as a single pipeline.

Not seven tools bolted together — seven stages that pass a shared, structured artifact down the line. A threat model aims the scan; the scan feeds triage; triage feeds the patch; the same verification bar governs a live incident. Each hand-off is machine-readable, so the pipeline runs end to end and a human reviews the output, not the plumbing.

The capabilities

What it actually does for you.

Threat modeling

Know what to worry about

Builds a structured threat model from an owner interview or straight from the code + history — assets, trust boundaries, scored threats, class-level mitigations.

Output: a map that aims every downstream scan and tells triage which findings matter.
Discovery

Find the bugs — two ways

Static source review across the attack surface, and an autonomous loop that crafts inputs and runs the target. Both, because different bugs need different lenses.

Output: candidate findings with file, line, class, and an attack story.
Verification

Prove it, don't claim it

For memory-safety bugs, an execution oracle builds the target under a sanitizer and only counts a bug when a crafted input actually crashes it, reproduced in a clean sandbox.

Output: reproductions, not assertions — the strongest signal there is.
Triage

Kill the noise

Independent adversarial verifiers re-derive each finding from source, drop false positives, collapse duplicates, and re-rank by real exploitability rather than the scanner's claimed severity.

Output: a short, ranked, owned worklist instead of a raw dump.
Remediation

From finding to fix

Generates candidate patches for the verified survivors, scoped to close the vulnerability class — not just the one reported line.

Output: reviewable diffs a human approves, not a ticket that sits.
Detect & respond

When the attacker is already in

Hunts application logs for compromise with no alert in hand, then works a lead end-to-end: did it succeed, how far, root cause, and a proposed response plan.

Output: confirmed incidents + a containment/remediation/recovery plan.

Why you can trust the output

The parts that make it more than a smarter scanner.

Proof, not probability

The execution oracle is the difference between "there might be a bug here" and "here is the input that crashes it." A verified reproduction can't be argued with — and a clean run means the tool works, not that your code is clean.

Reachability honesty

A real sink isn't always a real exploit. In one run, two genuine code flaws were flagged by static analysis — and the live pass proved the platform neutralizes both over HTTP. The harness tells you the difference; a scanner alone can't.

Adversarial by construction

Every finding is re-checked by verifiers whose job is to prove it wrong, independently, from the code. That's how a firehose becomes a ranked list you can hand to an engineer without apology.

Safe autonomy

It runs untrusted target code in a sandbox, hunts on read-only queries, and proposes response actions — it never blocks, rotates, or changes config on its own. Speed of a machine, blast radius of a reviewer.

Auditable method

Every hunt keeps a written hypothesis ledger; every number traces to a query you can re-run. The reasoning is the deliverable as much as the verdict — reviewable, not a black box.

Uncontaminated results

Trust a capability only on code the model has never seen. The discipline — original targets, answer keys kept out of the scanned tree — is what separates real discovery from recall.

The bar for any harness

What any system like this should be held to.

If you're evaluating this approach — from anyone — these are the properties that separate a real security harness from a wrapper around a model. Ask for all seven.

  • ✓
    Verifiable output. A finding comes with a reproduction or a traceable line of evidence — never just an assertion.
  • ✓
    Low, honest noise. False positives are actively hunted and dropped; severity reflects real exploitability, not category names.
  • ✓
    Full-lifecycle coverage. Model → find → prove → triage → fix → hunt → respond, not a single point tool.
  • ✓
    Auditable reasoning. A written trail — ledger, queries, votes — so a human can review the how, not just the what.
  • ✓
    Safe by default. Untrusted code sandboxed; response actions proposed, never executed; read-only where it should be.
  • ✓
    Adaptable to your stack. Retargetable to new languages, vuln classes, and domains — your code, your threat model.
  • ✓
    Human-in-the-loop. The output is a short list a person approves — the machine does the grind, not the judgment call.

The vision

An always-on security engineer that never stops at the finding.

It models the threat, finds the bug, proves it, prunes the noise, writes the fix, watches the logs, and works the incident — and hands a person a short, trustworthy, ranked list at every step. The firehose becomes a decision.
